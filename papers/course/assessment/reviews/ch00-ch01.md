## Chapter 1

### Critical

**1-C1. The machine's readiness condition is misstated.**
Line 316 (table row Q5, "Naive answer and why it is wrong"). Quoted: "an occurrence may run only after everything it reads is published and every other writer to that coordinate has contributed".
Problem: false. Spec 25.1 (CONTRIBUTE) requires only $\mathrm{Read}(o)\subseteq\mathrm{dom}(\sigma)$ and a defined body; contributions to one address may occur in any order. The wait for all writers belongs to PUBLISH (spec 25.2, "completion barrier": $U\cap\mathcal{C}_P(a)=\varnothing$). CONVENTIONS fact 6 states this. As written, $(s_1,j{=}0)$ would have to wait for $(s_2,j{=}0)$, which is not the semantics. It is also inconsistent with Ch1's own line 331 (three rules firing "in any order they allow").
Fix: "an occurrence may run once everything it reads is published, in any order relative to the other writers of its destination; an address is published only after every occurrence addressed to it has contributed".

### Major

**1-M1. The stated reason for guards is wrong.**
Line 122. Quoted: "The guard exists to make the set of contributions a function of the indices alone, so that it can be counted before any body is evaluated."
Problem: with an Iverson factor the set of contributions is also a function of the indices alone ($D_s$ is all of $\mathrm{Val}(\Gamma_s)$); the predicate depends only on indices in both uses (Ch1 line 111 says so). The actual difference (spec 8, 13.1, 14.4, 21.3) is that a guard removes valuations, so on removed valuations no body is evaluated, no primitive domain is demanded, and no read need be in bounds; an Iverson factor keeps the occurrence and its obligations (spec 14.4: "$\mathbf{1}_{i+1<4}X[i+1]$ without a guard does not satisfy the read rule at $i=3$").
Fix: replace the sentence with "The guard exists so that valuations it removes carry no obligation: their bodies are not evaluated, their primitives need not be in domain, and their reads need not be in bounds. An Iverson factor removes none of these obligations."

**1-M2. The description of the surface fragment contradicts the chapter's own examples.**
Line 167. Quoted: "The surface language accepts only an additive body of products of scalar factors, optionally under one unary operator or one marked slice operator. Anything more deeply nested must be written directly in core".
Problem: (a) The chapter never says what a "scalar factor" is. Spec 15.1: literals, named scalar reads, Iverson values, or registered unary operators on a named scalar read. Without this, line 119 (`Y[i] = 1_{i<1} log(X[i])`) and Exercise 4 look like they are not surface programs (a unary operator inside a product, not enclosing it). (b) Example 1.5's third statement `F(H[:,l])[i]` is neither of the two forms named: it is not the marked slice (`s.` syntax, spec 15.4) but the slice shorthand plus selection, which spec 15.1 (lines 571-578) classes as an explicit core scalar expression. The reader cannot tell which category it belongs to. (c) Line 119 writes `1_{i<1}` inside a `text` block without saying it is notation for the Iverson factor rather than concrete syntax.
Fix: after the sentence, add "Factors are literals, named reads, Iverson values $\mathbf{1}_Q$, and registered unary operators applied to a named read; a factor adds no reduction of its own (spec 15.1). The slice shorthand `H[:,l]` with a selection `[i]`, as in Example 1.5, is an explicit core scalar expression written in a short form, and a marked slice (`A[q,s.]`) is a separate abbreviation (spec 15.4)." Add to line 118 "(written here in mathematical notation)".
