# Chapter 7. Refinement and open problems

A compiled execution plan is another transition system. Its correctness is a simulation into the reference machine: plan steps may stutter, terminal outcomes must agree, and in the error-free profile a valid plan is never stuck. Lean proves this for a bounded plan profile and a bounded source fragment, and both the specification and the categorical proposal mark everything beyond those profiles as open.

## 1. From the reference machine to a compiled plan

[Chapter 5](05-operational.md) presents the reference machine as a finitely branching coalgebra on configurations. A compiled plan is a second transition system. Its states are concrete: a program counter $\mathsf{pc}$, a memory $M$ of physical slots, and layout metadata $\chi$. The specification writes a running state as $\mathsf{C}=(\mathsf{pc},M,\chi)$ with $\mathsf{pc}\in[m+1]$, where $m$ is the number of commands ([Part V, Section 30.1](../semantics/tensor_logic_semantics_part_v.md#301-concrete-command-execution)).

**Definition 7.1 (forward simulation with stuttering).** Let $\mathcal R$ relate plan states to reference configurations. Suppose every successful plan step $\mathsf{C}\to\mathsf{C}'$ from a related state is matched by a finite, possibly empty, reference segment $\mathsf{Conf}\to^*\mathsf{Conf}'$ with $\mathcal R(\mathsf{C}',\mathsf{Conf}')$. Then $\mathcal R$ is a forward simulation with stuttering.

Empty segments are allowed. A storage-only step matches none, and a batch may match many contribution steps ([Part V, Section 31.2](../semantics/tensor_logic_semantics_part_v.md#312-initial-states-and-successful-step-simulation)). The specification claims $\mathcal R$ only at command boundaries ([Section 30.4](../semantics/tensor_logic_semantics_part_v.md#304-the-refinement-relation-and-output-decoder)).

Simulation is not enough by itself. The specification says it "is not enough, by itself, to prove concrete termination or prevent an incorrectly stuck compiled execution." Its validity notion, Definition 31.1, therefore adds four semantic obligations to a static schedule check: initialization, the successful-step simulation, failure matching, and progress ([Section 31.1](../semantics/tensor_logic_semantics_part_v.md#311-acceptance-and-explicit-rejection)). The parts of Part V that supply these obligations are summarized below.

### Plan contracts (Section 29)

An execution plan has a finite buffer collection and a finite command sequence. Each command carries one of three annotations or, if it is fused, a finite sequence of them: $\mathsf{Accumulate}(G)$ for a set of tagged occurrences, $\mathsf{Publish}(B)$ for a block of addresses, or $\mathsf{Storage}(\theta)$ for a storage operation that changes no reference state ([Section 29.1](../semantics/tensor_logic_semantics_part_v.md#291-plans-commands-and-annotations)). An accumulation needs its group inside the unconsumed set $U$ and its footprint already published. A publication needs its addresses unpublished and no pending occurrence aimed at them ([Section 29.2](../semantics/tensor_logic_semantics_part_v.md#292-accumulation-and-publication-contracts)).

The schedule must satisfy four conditions ([Section 29.3](../semantics/tensor_logic_semantics_part_v.md#293-coverage-and-schedule-certificates)). Groups partition the occurrences. Blocks partition the defined addresses. Each read is published before the group that uses it. Each occurrence is accumulated before its address is published. A schedule with these properties yields a coordinate rank, so the ranked fragment is implied ([Part IV, Section 23.4](../semantics/tensor_logic_semantics_part_iv.md#234-coordinate-dependencies-and-the-ranked-fragment)).

### Concrete states and the representation relation (Section 30)

A published value is an immutable $\mathsf{pub}$ resource. An unpublished accumulator is an $\mathsf{acc}$ resource. A layout view places live resources in slots, and the simple profile of the specification requires it to be injective on the resources represented at once, and more permissive aliasing needs a separate justification ([Section 30.2](../semantics/tensor_logic_semantics_part_v.md#302-resource-views-and-live-representations)). The relation $\mathcal R_\Pi$ between a concrete state and a reference configuration includes the memory and layout equalities, agreement between the command prefix and the reference bookkeeping on consumed, published and remaining occurrences, and correct types and metadata ([Section 30.4](../semantics/tensor_logic_semantics_part_v.md#304-the-refinement-relation-and-output-decoder)). The Lean instance of the relation, in the specification's "As formalized" paragraph, adds reachability, a retention clause, and a clause that every slot outside the layout holds `none`.

Retirement clears a physical slot. The address stays in the published store as ghost history, and a later read of that address returns `none` ([Section 30.3](../semantics/tensor_logic_semantics_part_v.md#303-storage-changes-and-retirement)). The spec says that ghost information "may not supply kernel reads or returned values" ([Section 30.4](../semantics/tensor_logic_semantics_part_v.md#304-the-refinement-relation-and-output-decoder)). The output decoder reads each output from concrete memory. It never fills a missing coordinate with zero.

### Simulation and compiler correctness (Section 31)

A compiler may return a valid plan, or it may reject a source, a primitive, a dependency form, or a storage strategy. Rejection does not claim that the program has no model ([Section 31.1](../semantics/tensor_logic_semantics_part_v.md#311-acceptance-and-explicit-rejection)).

Lemma 31.2 (terminal adequacy) says that a valid plan reaching $\mathsf{pc}=m$ ends in a complete related reference state, and that its decoded output is that state's store restricted to the output tensors ([Section 31.3](../semantics/tensor_logic_semantics_part_v.md#313-failure-matching-progress-and-finishing)). Theorem 31.3 (compiled correctness) has three parts ([Section 31.4](../semantics/tensor_logic_semantics_part_v.md#314-the-compiled-correctness-theorem)). A decoded success $\zeta$ implies that the model set is a singleton $\{\rho\}$ with $\zeta=\rho|_{\mathrm{Out}}$. A matched failure at occurrence $o$ implies that the model set is empty. In the error-free profile, an error-free maximal run exists, every such run ends in decoded success or $\mathsf{PlanFailed}$, and the converse of (a) holds: the plan succeeds exactly when the model set is a singleton. (The Lean statement is phrased as `runPlan_not_stuck`.)

Theorem 31.3 is conditional on Definition 31.1. Conditions 3 to 5 are obligations on each kernel. For the slice 1 to 4 kernels, the generic steps and conditions 2 to 5 are checked in Lean. Every other kernel keeps its obligation. Beyond that profile the specification calls the result "a compiler proof specification with a mathematical argument, not a claim that a particular compiler or kernel has already been verified" ([Section 31.4](../semantics/tensor_logic_semantics_part_v.md#314-the-compiled-correctness-theorem)). No particular existing plan representation or compiler is assumed to satisfy these contracts ([Part V, introduction](../semantics/tensor_logic_semantics_part_v.md#part-v-compilation-and-refinement)).

**Example 7.2 (the running example).** Take $\eta_0$ from [Chapter 1](01-tensor-logic.md), where $Y[1]=0$. The only undefined occurrence is $(s4,())$. Failure matching allows only a ready undefined occurrence, so any matched failure on $\eta_0$ must name $(s4,())$. If the plan is valid and its run ends in $\mathsf{PlanFailed}$, Theorem 31.3(b) then says no model exists. On $\eta_1$, the fibre of $(Z,0)$ is $\{(s1,0),(s2,0)\}$. A plan may publish $Z[0]$ only after both occurrences are accumulated. The specification's example for this rule is a block published after one group while another group still contributes ([Section 29.3](../semantics/tensor_logic_semantics_part_v.md#293-coverage-and-schedule-certificates)). That example is about duplicate statements writing `T[i] = X[i]` twice, not about the running example.

### Batching and scans (Sections 32 and 33)

Lemma 32.1 says that a ready group applied in one batch gives the same accumulator as its members applied one by one. The reason is that $\oplus$ is associative and commutative ([Section 32.1](../semantics/tensor_logic_semantics_part_v.md#321-why-exact-batched-accumulation-refines-individual-steps)). The batch must keep every occurrence identity, including colliding ones. Array kernels must respect complete arguments and primitive domains, and an empty group evaluates no body ([Section 32.2](../semantics/tensor_logic_semantics_part_v.md#322-complete-arrays-empty-groups-and-shared-computations)). Fusing accumulation with publication is allowed only when the publication premise holds after removing $G$ ([Section 32.3](../semantics/tensor_logic_semantics_part_v.md#323-publication-fusion-and-interference)).

The separate-buffer scan of [Section 33.1](../semantics/tensor_logic_semantics_part_v.md#331-a-separate-buffer-history-plan) uses one buffer per time slice, which is $N+1$ buffers of capacity $d$, and it retains every slice. The rank $r(H,(i,l))=l+1$ orders its recurrence groups. A two-buffer schedule can produce the designated output $\mathrm{Last}$ with two state buffers. Its safety depends on a last-reader argument that the specification does not prove ([Section 33.2](../semantics/tensor_logic_semantics_part_v.md#332-reusing-two-state-buffers)). If $H$ is itself an output, every slice must be retained, so the two-buffer schedule cannot return only $H_N$ ([Section 33.3](../semantics/tensor_logic_semantics_part_v.md#333-full-history-outputs-change-the-retention-obligation)).

### Boundaries (Section 34)

Parts III to V separate three obligations: meaning, logical execution, and compiled realization. The compilation-layer proof targets cover typed annotations, resource views, single-kernel refinement, batching and sharing, concrete progress, terminal decoding, and scans. Each target carries one of three statuses. Most are proved for the slice 1 to 4 profile. Batching is proved only for the transactional singleton accumulate kernel, and sharing remains a target. The separate-buffer full-history scan is proved in slice 5, while terminal-only two-buffer schedules and their last-reader condition remain unformalized. The specification lists as outside the profile machine-number refinement, looser aliasing, asynchronous commands, general cyclic solvers, copy and relocation, dynamic allocation, cross-sort reuse, concrete allocation or kernel error sources, and a connection to the production backend ([Section 34](../semantics/tensor_logic_semantics_part_v.md#34-refinement-boundaries-and-formalization-targets)).

*For an agentic coder:* the claim to check is the simulation, not the final outputs. Section 34 says that testing final outputs "is useful evidence, but does not replace proofs of occurrence coverage, barriers, domain behavior, and safe reuse."

The table covers the reference machine, the static plan layer, and one bounded scan. It does not cover a production or backend refinement. The status text after the table says so directly: "No production/backend refinement is claimed."

The categorical proposal's Summary reports several proved results and states its own hedges. Five are most relevant here. The Summary also reports static composition, model composition, and operational associativity, which this chapter leaves out. The first is a witness-span category. Every validated input and complete model is packaged as a span between metadata-bearing whole-interface environments, and identities, composition, and associativity are proved. The second is a source functor. A certified source presentation has a genuine Mathlib functor into that witness category. The third is ranked operational composition. The composite rank certificate is proved from the two component certificates, and the actual runner completes the upstream part before any downstream action or fails upstream. The Summary calls this "an operational bridge toward a process interpretation, not a proof of process-category laws." The fourth is a ranked operational interpretation, with a source category, a full-observation target category, and a Mathlib functor. The fifth is an operational-to-witness comparison, an additive, nondefault layer. The Summary says it "does not supply a frontend/backend refinement," and that event order, intermediate histories, failure diagnostics, and assembly provenance are forgotten by the comparison. Broader source interpretations and backend refinement "remain separate obligations" ([Summary of the categorical proposal](../semantics/categorical_tensor_logic_semantics.md#summary)).

*For an agentic coder:* check the profile before trusting a name. A theorem in the table holds for the stated profile. A change outside that profile has no theorem behind it yet.

## 3. Open problems

The Lean path document lists the remaining work in dependency order ([Part 5, Sections 5.1 and 5.2](../semantics/lean_executable_semantics_path_part_5.md)). The paragraphs below follow that order only roughly: Part 5.2 puts floating point before general cyclic solving, and this chapter does the reverse.

**Beyond the bounded source fragment.** The first source slice covers finite read-only sums of products over bare slots. The remaining source work includes scans, marked arrays and slices, affine reads, guards and Iverson factors, nonlinear primitives, unpinned dimension inference, general substitution, rank synthesis, and schedule construction outside the fragment. Parser correctness and an independently specified raw denotation remain open ([Part 5, Section 5.1](../semantics/lean_executable_semantics_path_part_5.md#51-beyond-the-bounded-source-fragment)).

**Compiled and numerical refinement.** Nothing in the Lean development shows that the production compiler refines the semantics. Part V says that a refinement connection to the production `Eval/Plan` backend remains outside the proved profile ([Section 34](../semantics/tensor_logic_semantics_part_v.md#34-refinement-boundaries-and-formalization-targets)). The categorical proposal ranks one concrete frontend/backend refinement as its default first priority ([Section 10.3](../semantics/categorical_tensor_logic_semantics.md#103-remaining-branches-of-the-roadmap), item 1).

**Automatic scan recognition.** The bounded scan certificate of Section 33.1 is built for a given recurrence. The specification calls it "a constructed bounded scan certificate, not automatic source/scan recognition" ([Section 33.1](../semantics/tensor_logic_semantics_part_v.md#331-a-separate-buffer-history-plan)). The Lean path lists automatic general scan recognition as not yet done ([Part 5, Section 5.2](../semantics/lean_executable_semantics_path_part_5.md#52-later-compiled-and-numerical-refinement)).

**Buffer liveness.** The two-buffer scan needs a last-reader argument. A slice may be retired only after every recurrence occurrence that reads it has been consumed. The spec says terminal-only two-buffer schedules and their last-reader condition "remain unformalized" ([Section 34](../semantics/tensor_logic_semantics_part_v.md#34-refinement-boundaries-and-formalization-targets)). The wider buffer work also includes copy and relocation, retiring inputs, dynamic allocation, cross-sort reuse, and in-place kernels with snapshots ([Part 5, Section 5.2](../semantics/lean_executable_semantics_path_part_5.md#52-later-compiled-and-numerical-refinement)).

**General cyclic solvers.** A solver for general cyclic systems is not part of the reference machine, although the model relation still applies to cyclic programs. The specification says general cyclic solvers "remain a separately justified extension, not an implicit fallback" ([Part IV, Section 28](../semantics/tensor_logic_semantics_part_iv.md#28-reference-machine-boundaries-and-proof-targets)). The categorical proposal gives a related warning. Let $t=t^2$ and let $u=1/t$, defined only when $t\neq 0$. The upstream part has two models, $t=0$ and $t=1$. The downstream part excludes $t=0$, so the composite has a unique complete model, with $u=1$. The unique-model criterion is therefore not automatically compositional for arbitrary cyclic systems ([Section 9.3](../semantics/categorical_tensor_logic_semantics.md#93-why-unrestricted-partial-function-composition-is-unsafe)). Theorems 26.5 and 26.6 need the rank certificate ([Part IV, Section 26](../semantics/tensor_logic_semantics_part_iv.md#26-conservation-termination-and-correspondence)).

**Floating point.** Lowering $K$ to machine arithmetic is a separate refinement problem ([Part V, introduction](../semantics/tensor_logic_semantics_part_v.md#part-v-compilation-and-refinement)). Exact commutative pushforward laws do not imply bitwise schedule independence. A machine-arithmetic interpretation must state its reduction order or its numerical correctness criterion ([Section 28](../semantics/tensor_logic_semantics_part_iv.md#28-reference-machine-boundaries-and-proof-targets); [Part 5, Section 5.2](../semantics/lean_executable_semantics_path_part_5.md#52-later-compiled-and-numerical-refinement)). The verified runtime profile uses exact rationals. Separately, the bounded source layer's numerical profile claims exact bit agreement only for programs with f64-declared integral values of magnitude at most $2^{20}$ and one definition per left-hand side, and, in the status text after the table, "is not a floating-point semantics."

*For an agentic coder:* each open item is a place where a plausible optimization can silently leave the proved profile. Name the item before making the change.

## 4. How these notes adjusted the categorical proposal

The notes made seven decisions, five of which adjust the proposal. The last two, a running example and a mini Lean development, have no counterpart in it. Each decision is restated below with what the proposal says (where it speaks), what the notes do, and what is proved or only an analogy.

1. **Index layer.** The proposal treats additive pushforward as covariant functoriality of finite value families, and it does not establish a general pullback/pushforward adjunction or Kan-extension construction ([proposal, Section 4.1](../semantics/categorical_tensor_logic_semantics.md#41-additive-pushforward-and-its-laws)). The notes state the adjoint triple $\Sigma_f\dashv f^\ast\dashv\Pi_f$ on $\mathbf{Set}$-valued families and read it as Kan extensions along maps of discrete categories. They then decategorify to $K$-valued families and state the transpose identity $\langle f_! u,w\rangle=\langle u,f^\ast w\rangle$, which is proved directly. Proved on paper in [Chapter 2](02-index-categories.md), not in Lean: the triple for $\mathbf{Set}$-valued families. Analogy: the $K$-valued identity is the decategorified shadow of that triple. No adjunction on $K$-families is claimed as a theorem.

2. **Pure einsum.** The proposal says string-diagram and compact-closed presentations "must be justified for the chosen fragment," and they are not implied merely by using a symmetric monoidal operation theory ([proposal, Section 4.2](../semantics/categorical_tensor_logic_semantics.md#42-pure-einsum-fits-the-same-organisation)). The notes read pure einsum as composition in $\mathbf{Span}(\mathbf{FinSet})$, linearized, and use no string diagrams. Proved: the Lean correspondence of Proposition 19.1 for the bounded fragment. The span reading is a teaching organization, not a separate theorem in the table.

3. **Partial bodies.** The proposal says strict pairing makes $\mathbf{Pfn}$ symmetric monoidal but not Cartesian, since projecting one result still needs the other computation to succeed. It declines to install a general $\mathbf{Pfn}$ category ([proposal, Section 3.2](../semantics/categorical_tensor_logic_semantics.md#32-partial-functions-provide-a-useful-semantic-category)). The notes use $\mathrm{Kleisli}(\mathrm{Option})=\mathbf{Pfn}$, strict pairing as a monoidal product, and `sequence` as a distributive law. They do not use a domain-theoretic $\bot$ with an order, since the spec attaches no order to $\bot$ ([Part III, Section 18.1](../semantics/tensor_logic_semantics_part_iii.md#181-successful-and-undefined-results)). No row of the Lean table states the Kleisli identification. Treat it as the notes' organization.

4. **Models and denotation.** The proposal uses metadata-bearing whole-interface environments as the objects of its witness spans. The notes instead use plain sets: $\mathrm{Models}(P,\eta)$ is the equalizer of $\Phi_P$ and the inclusion, and the denotation is a span $\mathrm{Env}(\mathrm{In})\leftarrow\mathrm{Models}\rightarrow\mathrm{Env}(\mathrm{Out})$ up to span isomorphism. Partial functions are the case where the left leg is monic. Proved: the richer witness-span category, in the Lean experiments described in Section 2. The plain-set version is a teaching simplification of that content. The notes say that the Lean laws are for the richer objects. Models are all fixed points of $\Phi_P$ extending $\eta$ ([Part III, Section 20.1](../semantics/tensor_logic_semantics_part_iii.md#201-models-on-supplied-inputs)). There is no least-fixed-point selection ([Section 20.2](../semantics/tensor_logic_semantics_part_iii.md#202-a-partial-equation-operator)). The functional denotation is defined only on the functionally admissible inputs, where the model is unique ([Section 20.3](../semantics/tensor_logic_semantics_part_iii.md#203-functional-admissibility)).

5. **The machine.** The proposal says a coalgebra packages next-step behaviour, and it states that "No generic coalgebra instance or Turi-Plotkin distributive law is supplied by the prototype" ([proposal, Section 8](../semantics/categorical_tensor_logic_semantics.md#8-where-turi-plotkin-and-implementation-refinement-fit)). The notes use the machine as a finitely branching coalgebra over configurations, with the store-extension preorder as a thin category, invariants as subcoalgebras, the measure as a well-foundedness witness, and the rank certificate as a lax morphism into $(\mathbb N,<)$. These are organizing devices. They do not build a Turi-Plotkin distributive law, and the proposal lists that as an unexecuted pilot. Proved: termination through the measure (Lemma 26.4) and ranked progress (Theorem 26.5). Analogy: the coalgebra packaging.

6. **Running example.** The proposal has no counterpart. The notes fix one example with exact numbers, plus the finite-history scan example for ranks. This is a teaching choice.

7. **Mini Lean development.** The proposal has no counterpart. The notes keep a self-contained mini development separate from the production modules, and they cite the production modules by name rather than copying them.

**What the notes dropped.** The proposal discusses several structures that the notes leave out. The design record lists the St/Br syntax and Naperian typing as non-goals; Para and Markov categories are this chapter's own addition to that list. The structures are the St/Br graded PROP syntax, which the proposal calls "a serious syntax candidate" ([Section 7.1](../semantics/categorical_tensor_logic_semantics.md#71-stbr-remains-a-serious-syntax-candidate)) while saying it "is not assumed to be the best presentation of every layer" ([Summary, proposed next steps](../semantics/categorical_tensor_logic_semantics.md#summary)); Naperian typing in general, which the proposal treats as additional structure ([Section 7.2](../semantics/categorical_tensor_logic_semantics.md#72-naperian-representation-connects-compact-syntax-to-values)); Para, which the proposal calls "an interpretation layer, not a substitute for process refinement" ([Section 8](../semantics/categorical_tensor_logic_semantics.md#8-where-turi-plotkin-and-implementation-refinement-fit)); and Markov categories, since a normalization primitive "is not automatically a Markov-category construction" ([Section 8](../semantics/categorical_tensor_logic_semantics.md#8-where-turi-plotkin-and-implementation-refinement-fit)).

*For an agentic coder:* each decision above marks where a structure is proved, where it is an analogy, and where it is only a teaching organization. Before citing a categorical claim from these notes, check which of the three it is.

## 5. Where Turi-Plotkin would fit

Turi and Plotkin split an operational semantics into three ingredients: the shape of syntax, the shape of behaviour, and the interaction between them. Functorial descriptions capture the first two. The third needs a natural transformation of the right form, because an arbitrary transformation is not automatically an operational specification ([Turi-Plotkin document, Section 1.3](../semantics/categorical_operational_semantics.md#13-the-categorical-idea-identify-the-structure-behind-the-rules)). For the machine, a bialgebraic treatment would need a syntax functor for TL programs and plans, a behaviour functor for one-step observations, a rule transformation, and a compatibility law. The Turi-Plotkin document describes that law only as a compatibility law between the algebra and coalgebra structures, and defers its statement. The categorical proposal's own name for the missing artifact is a "Turi-Plotkin distributive law" ([proposal, Section 8](../semantics/categorical_tensor_logic_semantics.md#8-where-turi-plotkin-and-implementation-refinement-fit)). A treatment would also need a choice of observations, since two expressions with the same tensor value can have different execution steps ([proposal, Section 8](../semantics/categorical_tensor_logic_semantics.md#8-where-turi-plotkin-and-implementation-refinement-fit)).

Such a treatment would buy two things, for specifications that meet the framework's hypotheses. The first is that, for appropriate specifications, strong bisimilarity is proved to be a congruence, so equivalent components can replace one another inside larger programs ([Turi-Plotkin document, Section 2.2](../semantics/categorical_operational_semantics.md#22-a-reason-that-behavioural-equivalence-respects-constructors)). The second is a compositional bridge between execution and mathematical meaning, in which, under the relevant hypotheses, the behaviours of components determine the behaviour of the whole ([Section 2.3](../semantics/categorical_operational_semantics.md#23-a-bridge-between-execution-and-mathematical-meaning)). The framework also gives reusable theorems, so a new constructor need not be proved from scratch once the specification is shown to fit the framework. The Turi-Plotkin document says that this "does not eliminate proof obligations" but "moves them to a more reusable level" ([Section 2.1](../semantics/categorical_operational_semantics.md#21-reusable-theorems-instead-of-repeated-proofs)).

It is a pilot, not a result, as far as a general Turi-Plotkin law is concerned. The proposal does say that its Sections 6.12 and 6.13 already discharge a concrete constructor-behaviour compatibility obligation for the ranked sealed profile, directly from the runner and shared-cut algebra, without a general rule law ([Section 8](../semantics/categorical_tensor_logic_semantics.md#8-where-turi-plotkin-and-implementation-refinement-fit)). The proposal lists a bounded bialgebraic pilot as priority 2, with a decision gate. The pilot is promoted only if it expresses scope, provenance, and failure naturally, reuses the realization proofs, and materially simplifies adding constructors without relocating the same coherence obligations ([proposal, Section 10.3](../semantics/categorical_tensor_logic_semantics.md#103-remaining-branches-of-the-roadmap)). The proposal also says that sequential compositionality is already proved, so another presentation of it "is not by itself a stronger correctness result." For the current static fragment, it suggests that a finite-graph or history interpretation followed by simulation may be the simpler route ([Section 8](../semantics/categorical_tensor_logic_semantics.md#8-where-turi-plotkin-and-implementation-refinement-fit)). Turi-Plotkin itself does not promise that a compiler faithfully executes the rules ([Turi-Plotkin document, Section 3](../semantics/categorical_operational_semantics.md#3-what-the-approach-does-not-promise)). The simulation of Section 1 is still needed.

*For an agentic coder:* a bialgebraic framework would not remove the simulation obligation. It would only make constructor-level compatibility easier to state.

## 6. Why this matters for an agentic coder

The correctness obligation of any backend is a simulation into the reference machine. Section 1 gave the form of that obligation. A kernel that fuses commands, batches occurrences, or reuses memory must say which reference steps each command matches. A batch may match many contribution steps, and a storage change may match none ([Part V, Section 31.2](../semantics/tensor_logic_semantics_part_v.md#312-initial-states-and-successful-step-simulation)). The agent's first question about any change is therefore which reference segment the new code matches, and whether the terminal outcomes still agree.

Certificates are artifacts that a compiler must produce or reject. The compiler may return an accepted plan or an explicit rejection ([Section 31.1](../semantics/tensor_logic_semantics_part_v.md#311-acceptance-and-explicit-rejection)). A schedule yields a rank, but a rank does not justify overwriting a value that a later operation still needs ([Part IV, Section 28](../semantics/tensor_logic_semantics_part_iv.md#28-reference-machine-boundaries-and-proof-targets)). Layout must be injective on represented resources, and retirement must not clear a slot that another resource now occupies, since a second retirement "could erase a new occupant" ([Section 30.2](../semantics/tensor_logic_semantics_part_v.md#302-resource-views-and-live-representations); [Section 30.3](../semantics/tensor_logic_semantics_part_v.md#303-storage-changes-and-retirement)). The checker is the safety gate. The runner is not. The spec notes that "an unchecked live alias can still finish `done` with corrupted values" ([Section 31.1](../semantics/tensor_logic_semantics_part_v.md#311-acceptance-and-explicit-rejection)).

Fixtures and mutation controls are evidence, not proofs. The specification keeps this distinction explicit. The four-leg differential comparison of the bounded source layer "is executed evidence, not theorems" ([status text after the table](../semantics/tensor_logic_semantics.md#proof-status-and-numbered-results)). For the storage layer, the spec says the work "is validation of the existing storage model, not a scan-liveness theorem" ([Section 33.2](../semantics/tensor_logic_semantics_part_v.md#332-reusing-two-state-buffers)). A passing fixture supports a claim. A named Lean theorem proves the claim for its stated profile, and a claim outside that profile needs its own argument.
