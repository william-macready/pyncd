### F1 [Minor] On the `validateScheduled` path T2's F1 program still reports `cyclicDataflow`, not `multiWriterScan`
`validateScheduled` (`ScheduledValidation.lean`) runs `unless isTopoOrdered sched.stmts sched.stmts do throw .cyclicDataflow` BEFORE `collectDefinitions`, and `collectDefinitions` is what reaches `desugarMultiWriters`. `scanWriterConflict?` is "first" only inside the desugar.
Verified facts: `routeWrites` for `.scan` is `(base ++ recur names).eraseDups`, so scratch names ARE seen; `desugarMultiWriters` called directly on `[plain S := X, scan{scratch S}, plain U := S]` gives `multiWriterScan "S"`. Through `validateScheduled`, `eligible` for `U` sees `emitted.count S = 1` (scan scratch is never a publication) vs 2 writers, so the pre-check throws `cyclicDataflow "scheduled program: ..."` first. T2's F1 is therefore NOT surfaced earlier on the main entry; the user sees a misleading "cyclic dataflow" for a name conflict. Same for any program with a reader between a plain and a scan writer. Without a reader (`[plain S := X, scan{scratch S}]`) the pre-check passes and `multiWriterScan "S"` is reported.
Fix (Direct path, optional): in `validateScheduled` call `scanWriterConflict?` before the `isTopoOrdered` pre-check, or document in the `eligible` docstring that `cyclicDataflow` can shadow `multiWriterScan`. Add one hand-built fixture through `validateScheduled`; none exists (all T4 guards go through `desugarMultiWriters` only).
