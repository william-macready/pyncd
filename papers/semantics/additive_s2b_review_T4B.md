## Findings

### Major
M1. `confirmsSorted`'s `tropicalMultiFactor` arm does not require the two legs to agree with EACH OTHER (`SortedDifferential.lean:191-195`). It accepts `.mismatch l, .mismatch c` whenever both declarations equal the origin's. A checked-leg regression that yields different (still wrong) bits or a different first cell than legacy on the multi-factor tensor is classified `knownContractDifference` instead of `nativeDiscrepancy`. In every fixture both legs carry identical `observed`/`coordinate` (the old golden rows showed equal bits), so equality is the real contract. Failing input: `snap2 [a] [a] [multiY, bareV]` with a checked kernel whose max-times result differs from legacy's (e.g. checked returns the sum). Fix (one line): also require `l.coordinate == c.coordinate && l.observed == c.observed`, plus a guard with two hand-built `CellMismatch`es that differ only in `observed`.
M2. The multi-factor mismatch binding hides divergences in OTHER tensors, and the documentation understates it. `compareBindings` (`SortedDifferential.lean:84-94`) returns at the FIRST differing cell across all bindings. With head `multiY` (decl 6) confirmed, any unrelated native divergence on `V` (decl 7) is never examined: `[multiY, bareV]` with a wrong `V` still prints `multiFactor (some 6)`. The docstring (`:157-165`) and record §5 say only "a second divergence in the same tensor" / two multi-factor outputs. Required: reword to "no binding after the first mismatching one is compared"; optional hardening: for multi-factor, also require `compareBindings` over the bindings that do NOT descend from the origin to be `none`. Same for scatter-fill (see m3).

## Answers to the six checks
1. Detection vs confirmation. Multi-factor: confirmation reads the mismatch declaration, so it is bound to the origin tensor; a mismatch elsewhere is not confirmed (`!multi 6`). Scatter-fill: legacy `scatterFillNotIdentity name` (the stmt field is the tensor name, `Eval.lean:39`) and checked `scatterOptsNotAdmitted "{tensor}: fill"` (`Compile.lean:174`) must both name the origin tensor via `ownedBy`; other causes on either leg are false. No path confirms one statement's condition from another tensor's outcome. Caveat M1/M2.
2. First-mismatch binding: yes it can hide a mismatch elsewhere (M2), including other tensors; documented only for the same tensor.
3. Head-only and `fills ++ multis`: order is right (the fill refusal precedes any value comparison, so a head fill dominates; a multi head is never preceded by an unconfirmed fill). The head-only rule never confirms a non-head condition; the cost is noise (m4), not masking. Both-multi gives head decl 6 only (test:196-197).
4. Classification order: `confirmed` is consulted after `published` agreement and profile ok. Multi needs two `.mismatch` legs, which `legOf` cannot produce from failure/unavailable. Scatter-fill needs `legacy = .failure` of the exact error and `checked = .preparation` of the exact cause; `.unavailable` or a different failure never confirms. A genuine nativeUnavailable/nativeFailure therefore cannot be converted unless it IS the predicted refusal for the origin tensor.
5. Tests and manifest. The classification rows (`product`/`strided` x max/min, differing origins, both-shapes, accept-neighbour) fail if the logic regresses. Gaps: m1, m2. Manifest verified: JSON parses (18 cycles); each `old` string occurs exactly once in `SortedDifferential.lean`; `expect` lines match the intended guards: M3 -> 244 (`!multi 6`), M4 -> 230-233, M5 -> 232 (mixed natives with the other tensor's checked leg; 230/233 still false under the mutant, so "ONLY 232" holds), M6 -> 233 (same reasoning). `new` strings type-correct as reviewed; M3 only kills 244 because `known` rows keep their head confirmed.
