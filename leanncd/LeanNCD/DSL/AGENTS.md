# LeanNCD/DSL

## Purpose
Owns: the Lean-side twin of pyncd's TensorLogic DSL — parses `tl!{...}` surface syntax, elaborates to a typed AST, and proves properties of the compile→route pipeline that produces a routed DAG (`ThreadedComposed`). Two layers, strict one-way dependency: top-level files (`Syntax`→`Elab`→`Ast`/`Target`, plus `Traverse*`) own parsing/AST/UID-remapping; `Pipeline/` (`Types`→`Structural`→`Lowering`→`RouteSpec`) owns the 8-phase compile pipeline and its correctness proofs.
Does not own: evaluation semantics (`../Eval/`) or the acset bridge (`../Bridge/`) — both consume `DSL.Target`'s presentation types.

**House principle: fail loud, never silently drop semantics.** Cyclic dataflow, non-injective scatters, nonlinear scatters, inconsistent coupled-scan axis orders are all explicit `CompileError` variants, not silent miscompiles.

### Key Relationships
Strictly layered: `Syntax`→`Elab`→`Ast`/`Target`→`Traverse`/`TraverseAxes`→`Pipeline/Types`→`Pipeline/Structural`→`Pipeline/Lowering`→`Pipeline/RouteSpec`→`Compile`. `Pipeline/RouteFragments` hangs off `Pipeline/Types` **only** — it must stay importable without `Lowering`, since `Lowering` imports it and the reverse edge would cycle. That is why `LHSSlot.toReadIdx` and `producerSlots` live in `Ast.lean` rather than `Lowering.lean`: `splitStmt` and `physicalizeOne` build the nonlinear consumer's read coordinates, and degrade the producer's `.freeNorm` marker, from shared definitions, and only `Ast` is below both call sites (even though `Lowering` itself can now see `RouteFragments`, `RouteFragments` still cannot see `Lowering`, so a definition either call site needs still has to live below both). **One deliberate cross-layer exception**: `Structural.lean`'s header-comment-flagged `../Eval/Contract` import — its own header comment calls it "the ONLY cross-layer import on this branch," solely so `Stmt.uids_eq` and six `specsX_map_uid_eq` lemmas can state their RHS against `Eval.Contract`'s real UID collectors. Downstream: `Bridge/AcsetCodec.lean`/`Realize.lean` import only `DSL.Target`; `Bridge/Agreement.lean` imports `DSL.Compile` and `Pipeline.RouteSpec` directly. `Eval/*` imports `DSL.Ast`/`DSL.Compile`/`Pipeline.Types`/`TraverseAxes` — with one exception: `Eval/Plan/Compile.lean` (Wave F F4) also imports `Pipeline.Lowering` directly, reusing `idxToRow` to lower a scan's affine reads exactly as `Lowering.lean` itself does. Every other `Eval/*` file still never imports `Pipeline.Structural`/`Lowering`.

### Core Types
- `TLProgram { decls, stmts }`; `Stmt = assign | scatter | recurMorphism`; `LHSSlot = free | freeNorm | iterAt | iterNext | affine` (the scatter/plain/scan classifier); `Nonlin = identity | pointwise PointwiseFn | axiswise AxiswiseFn (Option BoolExpr)` (mask-typed-in by construction).
- `Decl = tensor | typedTensor TensorElementType .. | predicate | linear | axis | iter`, and `TensorElementType = f32` (one constructor today). **`typedTensor` is the ONE extensible typed-declaration constructor** — `tensor f32 X(i, j)` is `Decl.typedTensor .f32 …`, and a later `complex64`/`complex128` extends `TensorElementType` rather than adding a `Decl` constructor per dtype and forcing another exhaustive migration. `Decl.typedTensor` is tensor-bearing everywhere `Decl.tensor` is (declaration environments, rank checking, UID traversal, scheduling, routed categorical compilation), so every existing traversal must handle it — a wildcard-dropping arm silently loses the declaration. The categorical branch may erase the `.f32` annotation because it changes real-number *representation*, not the expression's scalar domain; **do not generalize that erasure to complex**, which is a different scalar domain.
- `ScanStmt = plain Stmt | scan (base recur : List Stmt) (isAffine) | scanPre` — post-`finalizeScans` unit grouping coupled recurrences.
- `ThreadedComposed { steps : List BrBaseP; routing : List (List Wire); nExternal }`; `Wire = external Nat | internal Nat Nat`; `StMatP { domLen codLen : Nat; coeffs; bias }` with `.wellFormed`/`.validate`.

### ScheduledProgram consumer inventory

- `prepareEvalPlan` and `evalScheduled` are the two public preparation/execution boundaries; both
  require `validateScheduled` and consume its declarations, explicit sizes, external-name order, and
  original statements. Its topology state advances by `ScanStmt.outputs`, not `writes`: recurrence
  scratch stays block-local, plain statements cannot read their own destination, and scan-internal
  state/scratch dependencies remain legal.
- `schedule` establishes the invariant for source programs. `capabilityPreflight` and
  `orderedExtNames` are preparation-phase helpers called only after the checked boundary.
- `elaborateAffineReindexings`, `routeCore`, `routeNameInventory`, `physicalizeRaw`,
  `physicalizeForRoute`, and `route` are routing/phase-local APIs. They either consume
  `schedule`'s result or enforce route-specific contracts; they do not silently invoke evaluation
  validation.
- `PropertyOracle.independentRun` remains an independent oracle with a valid-source precondition;
  its scan-free calls reach the shared boundary through `evalScheduled`, without coupling its
  unrolling logic to plan preparation.

### Physicalization case table (`RouteFragments.lean`, §2.4 of `papers/nonlinearity_split_pair_direct_lowering.md`)

`physicalizeForRoute` turns a **logical** `ScheduledProgram` (one statement per source statement, no
generated names) into the **physical** one `routeCore` consumes, expanding each nonlinear plain
assignment into a private producer/consumer pair. Every input class is classified explicitly by
`fragmentClass`; there is no catch-all arm anywhere.

`physicalizeOne` and `fragmentWidth` classify **independently** — `fragmentWidth` dispatches on `fragmentClass`, `physicalizeOne` re-matches the constructor surface because it needs the payload. `physicalizeOne_length_eq_fragmentWidth` ties them together on every class `physicalizeOne` *accepts*, so an arm that emits the wrong number of statements — or emits at all for a class `fragmentWidth` gives width `0` — fails to compile, and `fragmentLayoutOk` cannot rubber-stamp a `physicalizeOne` miscount. ⚠️ **That theorem is conditional on `.ok`, so it is vacuous on the reject class**: it closes only the dangerous direction (silently emitting a step for a class that must be rejected). Relaxing `fragmentClass`'s class-6 arm to `.copy` while `physicalizeOne` still throws typechecks fine — the guard for that direction is `test/DSL/Pipeline/RouteWeaveTest.lean`'s fixture 13 (`.scatter` door) and fixture 14 (`.assign` door), not the proof.

Two things a later reader should not misread as defects:

- **Class 6's rejection has no diff to point at.** `splitStmt`'s `.scatter` arm still says
  `-- always identity-nonlin here (rejected upstream otherwise)`, and that comment is still accurate
  *for `splitStmt`*, whose only caller chain runs `checkScatterNonlin` first. What changes is the
  caller set: `physicalizeForRoute` accepts a logical schedule from **any** caller, including a
  hand-built one that never passed validation, so the unenforced call-site precondition stops
  holding there. Copying such a node would route it as one `BrBase` with the nonlinearity silently
  absent from the categorical presentation. `unsupportedNonlinScatter` is reused rather than a new
  diagnostic minted, precisely because nothing reachable from `TLProgram.compile` can hit this path
  — so common-domain error constructor/payload/precedence are unchanged.
- **Classes 8/9 diverge from old `splitScan` on purpose.** `splitScan` splits nonlinearities
  *inside* scan base/recur bodies; physicalization copies the scan node verbatim. That is the
  scan-semantics fix, not a regression. It is still route-equal because scan routing is opaque
  (`toBrBaseP` uses a representative statement and the `BrOp` tag only, and `inputReadFactors`
  filters out self-writes — so the split intermediate never became a wire). Assert both halves
  separately: physical conservation (the body is byte-identical) and categorical projection
  equality (the routed steps/wires match). See `test/DSL/Pipeline/RouteWeaveTest.lean` F7/F8/F9.

## Patterns
`tl!{...}` flow (`Compile.lean`): Parse → **assignUIDs** (mint fresh UIDs per axis name) → **resolveDecls** (classify external vs. produced names) → **reclassifyIterSlots** (#5b: promote an `.affine (.shift a 1)` LHS slot to `.iterNext` iff `a` is declared `iter`, else `scanAxisNotIter`) → **checkReadRanks**/**checkDtypes**/**checkScatterNonlin** (validation, fail loud) → **lowerArith** (Phase 4: reclassify affine/diagonal LHS to `.scatter`; reject non-injective scatters without `reduce sum`) → **finalizeScans** (Phase 5: group `iterAt`/`iterNext` into `ScanStmt.scan` via union-find on shared iteration-axis UID) → **schedule** (Phase 6: topological sort, fail loud on cycles — the LOGICAL `ScheduledProgram`, this is `compileToScheduled`'s result) → **route** (Phase 7-8: `physicalizeForRoute` first expands each nonlinear plain statement into a private producer/consumer pair — `RouteFragments.lean`'s ten-class table — then the unchanged two-pass `nameToStep`/`extIndex` build and `buildStep` fold into `BrBaseP` steps + `Wire` routing). `splitNonlins` (`Lowering.lean`) is no longer on this chain — it survives only as a regression-only helper comparing the old split-then-schedule leg against the new logical-schedule-then-physicalize leg (`test/DSL/Pipeline/RouteWeaveTest.lean`).

## Pitfalls
- **`traverseAxes` is canonical** — `mapUID`/`specs*` are thin instantiations of `TraverseAxes.lean`'s generic traversal, not independent implementations. `unifyAxes`/`Exec/Context.lean` and all `*_eq_old` scaffolding are confirmed fully deleted (zero grep hits) — don't look for them.
- **`schedule` fails loud on cycles** (`Lowering.lean`) — the underlying Kahn's-algorithm `topoSort` silently falls back to source order on a cycle; `schedule` re-checks with `isTopoOrdered` and throws `CompileError.cyclicDataflow` explicitly, rather than letting a bad order surface later as an obscure eval-time error.
- **`buildStep_output_fixedAxes` (B.7) depends on `outputAxesConsistent`**, a fail-loud guard inside `buildStep` (`Lowering.lean`): a coupled scan whose **outputs** disagree on shared-axis order (e.g. `G[j,l]` vs. `H[l,j]`) is a compile error (`CompileError.inconsistentScanAxes`), not a silently-wrong output weave. This guard is what makes the canonical `ScanStmt.slotWeave` ordering sound — a change to that ordering ripples into `Bridge/Agreement.lean`'s `wf_typeMatch`. ⚠️ **Do NOT read this as covering base-vs-recur slot order for one tensor.** It compares the outputs of an *already-grouped* scan on the routed path, after grouping; nothing in `finalizeScans` checks that a base case and its recurrence agree on slot order (see the base-iteration-axis pitfall below). An earlier version of this bullet used `G[i,j]` vs `G[j,i]` as the example, which wrongly implied that gap was closed.
- **A declaration selects PRECISION, not just a name — and `bool` deliberately selects nothing.** `storageConstraintOfDecl` (`Ast.lean`) maps `typedTensor .f32` to `.float32`, `tensor`/`linear` to `.float64`, and **`predicate` to `none`**: a Boolean tensor is an algebra tag over whichever real carrier its graph selected, not a third carrier, so it contributes no constraint and a bool-only graph defaults to `.float64` (preserving every pre-f32 program). `storageConstraintOfName?` makes an **undeclared external real `f64`**, which is why an f32 graph reading one is mixed and rejected — every real external in an f32 graph must be declared `tensor f32`. `scheduleStorageKind` (`Pipeline/ScheduledValidation.lean`) scans in USED-NAME order (`orderedExternalNames` reads-then-writes, scan scratch included) and stops at the FIRST disagreement, so a graph with several conflicts names the earliest one. Two traps: a scan uses `ScanStmt.writes` (not `outputs`) so block-local scratch still constrains precision; and **unused declarations select nothing at all**, so adding a stray `tensor f32 Unused(i)` to an f64 program must not reject it.
- **`f32` is now a GLOBAL parser token, not an identifier.** `Syntax.lean` declares `syntax "f32" : tl_elem_type` for `tensor f32 …`, and a string literal in a `syntax` rule is a token in every module that imports it — so a bare Lean identifier named `f32` (e.g. `def f32 := …`, a binder, a field) no longer parses anywhere downstream of `DSL/Syntax.lean` (`unexpected token 'f32'; expected identifier`). Escape it as `«f32»` or pick another name. A future element-type keyword (`complex64`, …) will do the same to its own spelling.
- **`relu(where=...)` is unrepresentable by design, not omission**: `Syntax.lean` splits nonlinearity keywords into two *closed* categories (`tl_pointwise_kw` vs `tl_axiswise_kw`) — only the axiswise grammar production has an optional mask clause. This trades worse parse diagnostics for compile-time impossibility of a masked pointwise nonlinearity.
- **Scatter + nonlinearity is a currently-enforced restriction tracing to a real fixed bug**: `checkScatterNonlin` (`Structural.lean`) rejects any scatter/affine-LHS write with non-identity nonlin, because `Eval/Scatter.lean`'s `evalScatter` never applied `rhs.nonlin` — `Out[2*i] := relu(X[i])` used to compile and silently drop the `relu`. Documented as a "Spike-3 Stage-0 SHORT-TERM policy," not permanent — real nonlinear-scatter support needs a semantic decision (activate before/after collision-reduction) that's explicitly deferred.
- **Scatter-shaped scan-state writes are admitted only through S-B's narrow geometry.**
  `checkScatterNoScan` has been removed: `lowerArith` preserves the source placement as
  `Stmt.scatter`, and `compileScan` computes a dense `AssignPlan` before lowering the placement into
  `StateWriteMap`. Positive one-axis affine slots with nonnegative bias are allowed only in
  non-advancing dimensions, with zero fill, reject-on-collision, identity nonlinearity, and exact
  shared `LHSSlot.outExtent` agreement. Multi-axis/context-affine, scratch-scatter, predicate,
  nonlinear, non-default reduction, nonpositive, negative-bias, inconsistent-extent, and overlapping
  forms still fail loudly with typed located errors.
- **The `Eval.Contract` import in `Structural.lean` is a documented SPIKE EXCEPTION** — don't treat it as precedent for other cross-layer imports between `Pipeline/` and `Eval/`; reverting it means deleting the import together with `Stmt.uids_eq` and its six dependent lemmas.
- **Track A is complete except `readArityOk`** — everything else (uid-distinctness, M2/M3, #1's unconditional half) is fully proved; only the internal-read codomain-length tie needs the stated hypothesis.
- **WHITESPACE IS SEMANTIC in an LHS slot — CLOSED** (finding **#5b**, FIXED 2026-07-31). `ident "+1"` is still a single atom (`Syntax.lean`), but it no longer diverges in meaning from `+ 1`: both now elaborate to the same `.affine (.shift a 1)` (`Elab.lean`), so the old `nat`→`real` kind-flip and the degenerate `SCAN … axes=[]` it caused are both gone. The remaining distinction — recurrence vs. ordinary shifted write — is resolved one phase later, not at parse/elab time: `reclassifyIterSlots` (`Structural.lean`, runs between `resolveDecls` and `checkReadRanks`/`checkDtypes`/`checkScatterNonlin`/`lowerArith`) promotes an offset-by-1 shift to `.iterNext` **iff** its axis is declared `iter`; otherwise it throws `CompileError.scanAxisNotIter`. A new `iter <ident> = <num>[, <ident> = <num>]*` declaration (e.g. `iter l = 3`) is now the **only** way to declare a scan iteration axis — `axis l : ℕ = N` no longer suffices, by design (STRICT variant, so `Decl.iter` is a real invariant: present ⇒ iteration axis, pinned, ℕ-kinded). `RejectTest`'s RJ6 still rejects an undeclared iteration axis — same underlying defect — but now at **compile time** via `scanAxisNotIter` instead of the old eval-time degenerate-scan path. See `docs/superpowers/specs/2026-07-30-scan-axis-declaration-spike.md` (Parts 1/2a/3/4 now DONE) and `test/DSL/IterDeclTest.lean` for coverage, including mutation-tested spacing-equivalence and rejection checks.
- **An axis kind no longer carries a size payload at all** (finding **H**, FIXED 2026-07-30). It used to — `axis l : ℕ[3]` looked like an extent pin but pinned NOTHING (`AxisKind`'s `Option SizeExpr` was populated by the elaborator and read by nobody; `isNat`/`isReal` discarded it). Fixed at the type level rather than by adding a rejection: `AxisKind` is now the two-constructor `real | nat` with no argument, and the `ℝ[…]`/`ℕ[…]` grammar forms are gone — `axis l : ℕ[3]` no longer parses. **Extents still come only from `explicitSizes`' `.axis ax (some n)` fold (`Lowering.lean`)** — any "is this axis sized?" check must test the `Decl` payload, never the kind (that invariant didn't change, it's just unconditionally true now instead of needing a warning). `tl_size`/`elabTLSize` were kept (still used by `SizeExprTest.lean`; `papers/leanncd.md` §14.3 specifies `ℕ[n]` as an unfinished feature, not cruft — only the reachable no-op was removed). See `docs/superpowers/specs/2026-07-30-scan-axis-declaration-spike.md` Part 2b.
- **A scan base case does not name its own iteration axis** (finding **G**, PROBED 2026-07-30 — UNREACHABLE via surface syntax) — `G[j, 0]` ⇒ `.iterAt (scanAxis "") n`, **empty name** (`Elab.lean`). `adoptBaseIterAxes` (`Structural.lean`) recovers it from the matching step **by slot position**; on a miss it leaves the placeholder. The feared silent zero-fill doesn't happen for any `tlprog!` program: `assignUIDs` (`Structural.lean`) mints one fresh, mutually-distinct, non-zero UID per *distinct axis name* — `""` included — so two axes only ever share a UID if they share a name, and no real axis is named `""`. (Verified by direct inspection, not just inference: dumping `resolveDecls`'s output shows the placeholder relabeled to a real but distinct uid, e.g. `3` while `l`→`1`/`j`→`2` — it does NOT stay at its construction-time `0`.) So an un-adopted base's axSet always ends up disjoint from or a strict superset of its recurrence's real axSet — `missingBaseCase` or `inconsistentScanAxes` fires loud, every construction tried. Only a hand-built AST bypassing `assignUIDs`'s name-based minting entirely could make this silent — don't detect a placeholder by `uid == 0` in new code on that account (that was never the actual invariant), but no fix is needed for the surface DSL. See `papers/semantic_payload_audit.md` finding G and the #5b spec's Part 5 (closed docs-only).
- **`splitStmt`'s linear (`.identity`) half must NOT carry the original `.freeNorm` marker** (found and fixed 2026-08-21, leanncd Thread 4 Task 3). `splitStmt` (`Lowering.lean`, Phase 6) splits any non-`.identity` statement into a linear step (writes a fresh `%nl{uid}` intermediate, `nonlin := .identity`) plus a nonlin step (reads that intermediate, carries the original `Nonlin`) — and BOTH steps used to reuse the exact same `slots` list, so a `.freeNorm`-marked axiswise statement (e.g. `Y[q, s.] := softmax(A[q, s])`) left the marker on the linear half too. **This split path is NOT obscure — it runs constantly**: every real Portfolio softmax/normalize/l2normalize fixture (`NormTest.lean`, `AttentionTest.lean`, `GenerativeTest.lean`, …) feeds a `.freeNorm`-marked program through it via `TLProgram.compileToScheduled`/`TLProgram.eval` today. It does not, and has not since 2026-08-27: `freeUID?` returns `some a.uid` for **both** constructors (the "fourth class-6 door" fix, documented in `Ast.lean`'s own docstring), precisely so that `Y[i,i]` and `Y[i, i.]` are detected as the same diagonal LHS. `slotsBecomeScatter` therefore cannot observe the marker's value at all. The function that still discriminates by value is **`LHSSlot.normUID?`** (`.freeNorm` only), reached through `normAxisUidOf`. That is why leaving the marker on the linear half was safe pre-Thread-4: not dead code, but a value no live downstream consumer could observe. Fixed by degrading `.freeNorm → .free` on the linear step's OWN slots only (`linSlots`, `Lowering.lean` in `splitStmt`) — the nonlin step keeps the original marker unchanged, since that is the statement `resolveNonlinAxis` needs to see it on. Any check that reads the marker's value after `splitNonlins` can observe the degraded `.free` on the linear half, and this analysis then needs re-checking.
