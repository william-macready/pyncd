# LeanNCD/Eval/Plan

## Purpose
Owns: the checked, positional evaluation backend — a source compiler to a raw plan graph, checkers that turn it into private-constructor evidence, dense workers that run only that evidence (binary64 and native binary32), named↔positional adapters, and the experimental JAX executable phase. Independent of the legacy `Gather`/`Contract`/`Scan` evaluator in the parent directory, which remains the ground-truth reference it is differentially tested against.
Does not own: reference semantics (`../AGENTS.md`), source parsing and scheduling (`../../DSL/`), the JAX code generator (`experiments/jax_bridge/`).

Design records, not duplicated here: `papers/wave_c_capability_manifest.md` (Wave C), `papers/wave_f_scanplan_proposal.md` and `papers/wave_f_capability_manifest.md` (checked scans), `papers/eval_ir.md`, and each slice plan's close-out (`papers/f32_evalplan.md`, `papers/f32b_evalplan.md`, `papers/scatter_affine_lhs_writes.md`).

## Code Map

## Contracts
- **Evidence is the only way in.** Every worker takes private-constructor checked evidence; no raw-plan-plus-ops entry is exported. A checker reuses the local checkers' obligations instead of re-deriving them (`checkPlan` dispatches `checkAssign`/`checkScatter`/`checkScanPlan`/`checkPointwise`/`checkAxiswise`; `checkPlanBlock` reuses them plus `checkStepGraph`).
- **One formula, two carriers; storage kind keeps them apart.** Binary64 and binary32 share each traversal through a private ops record (`ScalarKernelOps`, `NonlinScalarOps`) and differ only in the instance. Checked evidence records the `storageKind` it was checked for. **Every worker and adapter core checks that kind as its FIRST statement**, before arity or store work, and a mismatch is `storageKindMismatch`, never a conversion. The one ordering exception: the named `pack`/`unpack`/`pack32`/`unpack32` entries run `checkPreparedBindings` before reaching their core's guard (the runners' guard runs before bindings). Fixtures pin guard ORDER, not just existence. A new door needs its own guard; a new carrier follows the f32 shape (a `kind` parameter on each checker core, an ops instance, a graph worker beside `Dense32.lean`, a `StorageCarrier` instance and named boundary, and a guard at every door in `papers/f32_evalplan.md` §3.5).
- **Current binary32 boundary.** Admitted in a `.float32` graph: `.assign`, `.pointwise`, `.axiswise`, inline unary reads. Refused: `.scatter` and `.scan`, at compile time (Step 0c: `"{nm}: f32 scatter"`/`"{nm}: f32 scan"`), at `checkPlan` (`f32UnsupportedStep i kind`, over original step indices), and at `runDensePlan32`. `runDenseScatter`/`runDenseBlock`/`runDenseScan` are Float-only and are safe only because of those refusals — F32-D and F32-C inherit them.
- **`ScalarDType.bool` is a semantic algebra/signature tag over the graph's REAL carrier, never a carrier of its own.** Each `ScalarKernelOps.decodeConst` decodes `.bool` to that carrier's exact one/zero. `deriveStorageKind` picks the carrier from the signature table, and `bool` contributes no constraint. (a) The DESTINATION selects the algebra (`admittedAlgebrasFor`: `f64` gets sum-product plus both tropical semirings, `bool` gets `admittedAlgebraBool`, `f32` gets nothing — binary32 uses `admittedAlgebrasForF32`). (b) Source/destination dtype equality is NOT an assignment obligation; `PlanError.dtypeMismatch` is producer-less. (c) Runtime values are NOT restricted to `0`/`1`, matching the reference evaluator. (d) Declarations are authoritative: `buildDeclEnv` rejects a repeated name, and a contradicting signature is `InputSignatureError.dtypeMismatch`.
- **The write-geometry surface stays exhaustive over `WriteRowKind`.** Nine match sites (six in `Scan.lean`, one in `Compile.lean`'s base-write placement, two in `ScanTest.lean`'s frozen `stepWriteRowsOkNoClause1` oracle) have no wildcard, so a new kind is a compile error at each. The tripwire forces a decision, not a sound one: discharging every arm with `true` compiles and recreates the defect. **Not tripwired, and must be extended by hand:** `classifyWriteRow` (produces kinds), `causalAdvancingRow` (read rows), `baseWriteTouchesBoundary` (decides by equality), and `ScanTest.lean`'s `allRowKinds` list. `.strided` is admitted only with positive scale and nonnegative bias, at non-advancing state dimensions, with `scatterDestExtent` extent agreement; equal-scale distinct residues prove base writes disjoint. `Scan.lean`'s module docstring is authoritative. This family's recurring defect is a predicate saying which rows MUST be a kind but not which MAY NOT be.
- **`checkScanPlan` owns dtype positions no `checkAssign` sees** (`stateDtypeNotAdmitted`, `captureDtypeNotAdmitted`). `CheckedScanPlan` stores the signature table it was validated against; `runDenseScan` requires the caller's table to equal it (`signatureContextMismatch`) and the store length to match (`storeArityMismatch`) before allocating or committing anything.
- **A block's `.pointwise`/`.axiswise` source must be a PRECEDING `.assign` destination** (`nonlinearSourceNotLocalAssignment`) — what keeps `Scan.lean`'s assignment-only causality walk complete.
- **Error-constructor shape, not step kind:** a `checkScatter` failure surfaces as `PlanStepError.assign (.nodeError ni e)`, because the payload is a plain `PlanError`.
- **JAX is binary64-only and context-free, gated at two levels.** Per node, `checkJaxAssignSupport` rejects (located, in the order destination/algebra/context/factors) a Boolean destination or source, tropical max/min, a unary read, and a non-empty `contextShape`. A `.scatter` is refused categorically (no `checkJaxScatterSupport` exists: neither lowering represents placement, `fill`, or collision); `JaxExecutableWellFormed` admits only an `.assign` step at a kernel's index. Per PLAN, a non-`.float64` plan is refused FIRST — `validateAndConstructExecutable` (`unsupportedStorageKind`) and all seven `EvalPlanCodegen.lean` doors via `requireFloat64Plan` — because a zero-step f32 plan passes every per-node check vacuously. A new JAX entry point needs its own `requireFloat64Plan`. Certification implies rendering: `validateEinsum` mirrors the emitter via `einsumTermRenderable` and the public `einsumTermLabelExtents`, which `lowerAssign` also calls — every factor's source extent must equal its label's iteration extent, since a shorter zero-padded read renders as `a->a` and returns a different shape than Dense. Which NAME belongs to which slot is deliberately not re-checked there (`raw` carries no names).

## Pitfalls
- **"Admitted by the checked backend" ≠ "runs on JAX" ≠ "runs in binary32".** Check each boundary separately (Contracts).
- **A (c) cell is a guard dependency, not a pass.** `runDenseScatter`, `runDenseBlock`, and `runDenseScan` compute through Float-only helpers and are correct only because f32 scatter/scan never reach them. Removing a refusal without making the worker carrier-parametric is false f32.
- **No legacy oracle exists for f32.** Binary32 fixtures assert exact `Float32.toBits`; never derive them by narrowing binary64 results.
- **Don't delete producer-less constructors** (`dtypeMismatch`, `unaryNotAdmittedForStorage`, …) — they are retained on purpose.
